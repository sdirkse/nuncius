# 5. Sandboxed targets, no network by default

Status: accepted · 2026-10-17

## Context
Targets act autonomously and read untrusted content. A worktree protects the project, but not the rest of the machine.

## Decision
"As safe as possible inside the worktree":
- Codex: `--sandbox workspace-write`, with network off.
- Cursor: the CLI's sandbox mode, writes limited to the worktree, with network off.
- Claude: `--permission-mode dontAsk`. Read, edit and search are allowed, and Bash runs only inside Claude Code's bash sandbox (worktree only, no network).
- A task may request `network: true`, for example to run `npm install`.
- There is **no** full-access mode. Flags that bypass the sandbox or approvals are never used.
- If a target's sandbox turns out not to work headless, that target falls back to a fixed per-project command allowlist. It never falls back to full access.

## To verify
How Cursor's and Claude's sandboxes behave in headless runs, checked against the real CLIs.

## Implementation notes (2026-10-17)
- Two layers. The **outer** layer, for every target, is a `sandbox-exec` (Seatbelt) profile that Nuncius generates per task. It restricts files: writes are allowed only to the worktree and the task's own per-task scratch dirs, the caller's checkout is never writable, the CLIs' config/hooks/MCP files stay read-only, and `~/.nuncius` and a blocklist of credential, history and browser-data paths are unreadable (see the read/write policy note below). The **inner** layer is the target's own sandbox for the commands it runs: Codex `workspace-write`, which also controls network.
- The outer layer does not block network, because the target CLI needs it for its API.
- Cursor gets `--force` from Nuncius (never from callers), because the outer layer confines its writes. Network for Cursor's commands stays unrestricted until its CLI sandbox flags are verified.
- With the outer layer in place, a nested `nuncius` call from inside a task cannot read or write `~/.nuncius`. That closes the setsid escape noted in ADR 8.
- `sandbox.extraWritable` and `sandbox.extraDenyRead` in the config adjust the profile.
- Seatbelt is macOS only. Other platforms are refused until there is an equivalent (e.g. bubblewrap on Linux).

## Egress through a per-task proxy (2026-10-17)
- macOS refuses to apply a nested Seatbelt profile (`sandbox_apply: Operation not permitted`). The CLIs' own sandboxes (Codex `workspace-write`, Claude Code's Bash sandbox) therefore cannot run inside Nuncius's sandbox. They are switched off, and Nuncius's profile covers both files and network.
- **Network:** the profile allows outbound connections only to a per-task CONNECT proxy on loopback (`src/proxy.js`). It allows only TLS on ports 443 and 80, refuses IP literals, and only lets through the target's `apiDomains`, plus `network.domains` when the task has `network: true`. The proxy resolves names outside the sandbox. Targets get **no DNS**: the resolver socket and the mach services are denied, so hostnames cannot be used to smuggle data out.
- **Residual risk: the vendor API itself.** Commands that a target spawns inherit the proxy settings, so they can reach the same API host as the target CLI, even with `network: false`. A target that has been prompt-injected *and* given an attacker's own API key could send readable data to that attacker's account on the vendor's API. TLS hides the request contents from the proxy, and Seatbelt cannot tell the CLI and its children apart by process. We accept this for now and keep `apiDomains` as narrow as each CLI allows. A proper fix would need a per-process network identity, for example running commands as a separate user, or a vendor-side allowlist.

## Verified with the real CLIs (2026-10-18)
- **Codex 0.163:** works through the proxy and needs only `chatgpt.com` and `ab.chatgpt.com`. Calls to `*.oaiusercontent.com` (file storage) are refused, and tasks still succeed, so they stay refused.
- **Cursor CLI 2026.10.16:** needs `*.cursor.sh`. It writes `cli-config.json` and `projects/` under `CURSOR_CONFIG_DIR` / `CURSOR_DATA_DIR`, and it loads plugins and their MCP servers from `$HOME/.cursor/plugins`. With the real HOME, it tried to connect directly to the user's MCP servers (`mcp.context7.com`, `mcp.atlassian.com`). The sandbox correctly blocked those connections, but they caused roughly 60 seconds of timeouts. Cursor therefore now gets a throw-away HOME, with a copy of the CLI settings and a link to `~/Library/Keychains` for the login. A task went from about 70 seconds to about 9.
- **Not carried into tasks:** the user's MCP servers and plugins. Cursor no longer sees them because of the separate HOME, Codex because `config.toml` is no longer linked, and Claude because of `--strict-mcp-config`. A delegated task should not get the user's personal integrations.
- Cursor still tries `http://localhost/getRepositoryInfo` through the proxy (refused) and some direct connections (blocked). Tasks succeed regardless.

## Read and write policy tightened (2026-10-21)
A multi-model red-team review found the outer profile broader than this ADR claimed:
- **Writes.** The profile allowed writes to all of `/private/tmp` and the per-user `/var/folders` temp, beyond the per-task `TMPDIR`. A target could plant files there for another program or a later task to read. Those broad grants are removed: a target may write only its worktree and its per-task scratch dirs (`TMPDIR`, cache, the throw-away Codex/Cursor home), which are redirected there by env. Exception: Claude Code keeps its shell-snapshot workdir at `/tmp/claude-<uid>` (hardcoded, not following `TMPDIR`) and writes a per-shell `/tmp/claude-<hex>-cwd` file. The Claude profile allows only this run's own subdirectory there — the one Claude derives from the working directory by turning every non-alphanumeric character into `-` — plus creating the shared base dir and the `/tmp/claude-<hex>-cwd` filename shape (a Seatbelt `regex`). Nuncius itself creates the base dir (mode 0700) before the task starts, and the profile grants no write on the base — only on the per-run subdirectory — so a Claude task cannot write into another session's or another task's snapshot workspace there, nor unlink the base or plant a symlink at it (both flagged by an automated security review when the base was reopened). If the base is not a directory Nuncius can create and own, the snapshot allowance is dropped (Claude's Bash degrades but stays safe). The per-shell cwd file's random hex is not predictable, so that one rule stays a shape match; it only affects Claude's own cwd tracking. Verified: Codex, Cursor and Claude all run; a real-CLI check was repeated after the write rules were fixed, because an empty allow-list had briefly produced a bare `(allow file-write* )` rule that allows everything — now there is a test that the profile never emits a bare allow-all rule.
- **Reads.** "No reads of common credential stores" was too narrow: the list was a handful of cloud-credential dirs, while shell history (which often holds tokens pasted on a command line), `~/.gitconfig`, `~/Library` cookies and app token stores, and other repositories were all readable. The deny list is expanded to cover shell/tool history, more credential and infra stores, git/DB config that can carry credentials, and browser cookies/session storage. It remains a blocklist, not a proof: a target runs with the real `$HOME` for Codex and Claude, so the honest statement is that the common secret locations are blocked and the user should keep secrets out of delegated repositories and use `sandbox.extraDenyRead`. The macOS keychain is deliberately left readable — it is encrypted and gated by securityd (not raw file reads), and Cursor and Claude read it for their own login; denying the file broke their auth without protecting the secrets.

## Second red-team round (2026-10-21)
- **Inbound connections bypassed the proxy.** The profile denied only `network-outbound`, so a target could listen on an IP socket — including `0.0.0.0` — and exchange data with anything that connected to it, which is a channel past the proxy allowlist. Reproduced: a listener inside the Codex profile received data from a client outside the sandbox. The profile now denies `network-bind` and `network-inbound` for IP sockets. Unix sockets (local IPC) are unaffected, and nothing that worked before is lost: outbound connections to any loopback port other than the proxy were already denied, so a target could never reach its own test server anyway. Verified with the real Codex, Cursor and Claude CLIs.
- **Residual: other terminals.** `/dev` stays writable, because the CLIs create pseudo-terminals for the commands they run and Seatbelt cannot tell a task's own pty from another one. A target can therefore open another terminal of the same user (`/dev/ttysNNN`) and write to it. Reproduced, accepted for now; the fix is the same per-user separation as for the vendor-API residual.
- **Residual: a `setsid` descendant outlives the task.** Nuncius kills the target's process group at the timeout; a child that moved to a new session survives (reproduced: it kept writing for seconds after the task ended). It stays inside the sandbox, so it can still only touch the worktree and the task's scratch dirs, but it can change the worktree after Nuncius has committed it. Review the diff against the commit Nuncius reports, not the live worktree. Since then Nuncius also stops, before it commits, every process started since the task that works in or runs from the task's own folders (`src/strays.js`; Cursor's updater left the group this way). A complete fix needs a task-wide containment boundary: task accounts (ADR 12) for Codex and Claude, or a VM.
- **Cursor with a very long Nuncius home path.** Cursor puts a socket path under its project dir and falls back to `/tmp/.cursor` when that path would exceed the macOS socket-path limit; `/tmp` is not writable for a target, so Cursor then fails. This only happens when `NUNCIUS_HOME` is set to an unusually long path; the default `~/.nuncius` is fine.

## Verified CLI versions (2026-10-22)
Nuncius depends on undocumented CLI behaviour (Claude's snapshot dir naming, Codex's app-server API, each CLI's API hosts and output format), so an update can break it silently. `src/versions.js` lists the versions last run end to end against the real CLIs under Nuncius's sandbox: Codex 0.163.0, Cursor 2026.10.16 and Claude Code 2.1.299 (the smoke tests for the inbound-network change). A version outside that range gets a warning, never a refusal: in `nuncius doctor`, in MCP `list_targets` (`version`, `version_note`) and on each task run. A run only uses a version a check already read (cached per binary build): it never starts the CLI outside the sandbox just to ask. Widen a range only after running the real CLI through Nuncius.

## git inside tasks (2026-10-23)
Denying `~/.gitconfig` (read policy, above) broke git for Codex and Claude tasks, which run with the real `$HOME`: git treats an unreadable global config as fatal, so every `git status`, `git log` or `git diff` a target ran failed with "unable to access '~/.gitconfig': Operation not permitted". Cursor tasks were unaffected (throw-away HOME). Found while tracing the CLIs' home-folder reads. Targets now get `GIT_CONFIG_GLOBAL=/dev/null`: git runs with no global config, which is also the safer default, because the user's credential helpers, url rewrites and aliases do not apply inside a task. The caller cannot override it through `sandbox.passEnv`.

## Home folder: an allowlist (2026-10-23)
The read policy was a blocklist of known secret locations; everything else in the home folder was readable, including other repositories, the caller's ignored files (`.env`), shell config and app data. It is now an allowlist: the profile denies `file-read*` on the whole home folder, then opens only what a task needs. The list came from tracing the real Codex, Cursor and Claude CLIs under a home-wide deny and fixing each failure (unprivileged processes cannot read sandbox denial logs on macOS 26, and the old `trace` directive is gone):
- the task's worktree and scratch dirs (as before);
- the repository's shared git dir behind the worktree (`commondir` of the worktree's git dir, recorded by Nuncius before the target runs): worktree git commands need its objects and refs. The caller's working files are not included;
- the link that starts the CLI, the folder it is in (macOS `realpath(3)` reads a link's folder; Cursor's start script resolves itself) and the CLI's real install folder; Codex's `auth.json` (linked into its per-task home); `~/Library/Keychains`;
- every `PATH` folder inside the home folder, a fixed list of toolchain homes and package caches (rustup/cargo, nvm, volta, fnm, bun, deno, pyenv, rbenv, asdf, mise, pnpm, conda, dotnet, Go modules, Maven and Gradle caches, the npm cache), and `sandbox.extraReadable`. `~/.cache` is not on it (mixed app data, tokens included);
- the folders above all of these: `file-read-metadata` only, so paths resolve and `getcwd` works while the folder itself cannot be listed.

The secret denies still come later, so credential files inside readable folders (`~/.cargo/credentials.toml`, `~/.m2/settings.xml`, …) stay closed. git inside a task also gets `core.excludesFile` and `core.attributesFile` set to `/dev/null` (the global ones are unreadable and git warns on every command otherwise).

**A Seatbelt detail found on the way:** a rule naming a specific operation (`file-read-data`) wins over a rule using the wildcard (`file-read*`) regardless of order; "last matching rule wins" holds only between rules of the same kind. The profile therefore uses `file-read*` throughout, with `file-read-metadata` only where that precedence is wanted (the folders above allowed paths).

Verified with the real CLIs: Codex and Claude ran cargo, rustc, pnpm and git; `~/.zshrc`, the caller's working files and listing the home folder were refused. Cursor works too; its rustup finds no toolchain because Cursor runs with a throw-away HOME (as before this change). A Nuncius installed in the home folder can no longer be started from a task at all, before the canary is even reached. `nuncius doctor` now also checks that a file in the home folder is unreadable.

### Follow-up after an automated security review of the allowlist
- **The repository config was readable.** Opening the shared git dir opened `.git/config`, which can hold credentials (a token in a remote URL, `credential.*`) and settings that run commands (`core.fsmonitor`, `core.sshCommand`). git cannot run without a readable repository config (verified: it stops with "unable to access … config"), so the config is now denied and a task's git gets a per-task shadow common dir through `GIT_COMMON_DIR`: links to the real objects, refs and the rest, and a config with only the `extensions.*` settings and a fixed set of harmless `core.*` keys. Verified with the real CLIs: git works, `git remote -v` shows nothing, a token in the remote URL never appears.
- **Folders from the environment could be broad.** A `PATH` entry or a CLI install folder in the home folder is now opened only when it is at least two levels deep (`~/.cargo/bin`) or a top-level `~/bin`, so a `PATH` containing the home folder itself or `~/Documents` opens nothing, and a CLI installed directly in the home folder opens only its own file.
- **More credential files in toolchain folders:** `~/.cargo/config(.toml)` (registry tokens), the conda `.condarc` files and pixi's config are denied.
- **Second review round:** per-worktree git config (`config.worktree`, in the common dir and under `worktrees/<id>/`) is closed too, and the shadow config leaves out `extensions.worktreeConfig`, so git reads no such file. Folder checks now use the real path, which is what the profile opens: a `~/bin` or toolchain folder that is a link to the home folder opens nothing.
- **Third review round:** "outside the home folder" was treated as safe, but a folder outside it can *contain* it (`/`, `/Users`, or a toolchain link to either), which would reopen everything. Now no folder the profile opens may be the home folder or contain it, whatever its source: `PATH`, the toolchain list, the CLI's install folder or `sandbox.extraReadable`.
